### 1.4 P1 ①：`/api/breadth_880.json` prev==today（证实并升格）

**活体三端口实测（2026-10-24 周六 ~19:55）：**

| 端口 | today.date / up / limit_up | prev.date / up / limit_up |
|---|---|---|
| 8800（旧） | 20261024 / 4526 / 84 | **20261022** / 535 / 33 |
| 8810（生产 v2） | 20261024 / 4526 / 84 | **20261023 / 4526 / 84 —— 值与 today 全等** |
| 8819（我的临时实例，同代码） | 同 8810 | 同 8810 |

R1 自报属实，且比自报更重：**这不是临时实例的问题，生产 8810 现在就在下发 prev==today**（周末用户打开广度 880 块即见「昨日=今日」）。

根因（源码层定位）：
- 新链 prev 取「日期严格小于今天(自然日)的最后一根 bar」（`app/plugins/compat_sector/backend.py:611` `row[0] < t_int`），数据源是 `ctx.quotes.daily_bars` → eltdx `bars.get`（`app/core/quotes.py:262`），远端日线在非交易日已含最近交易日（20261023）的 bar；today 同源快照在非交易日返回的也是该日收盘值 → prev==today。
- 旧 8800 同一 `_pick` 语义（`engine/server.py:991-995`），但它读本地 vipdoc `.day`（末根现停 20261022）→ 给出 20261022。两端语义相同、差异纯来自数据源新鲜度。
- 附带发现：8800 的 prev=20261022 也非正确语义（上一交易日应为 20261023）——旧端在周末同样在错，只是错得不同方向。**修复口径建议**（给 compat_sector owner）：prev 应取「严格早于最近交易日的 bar」，或引入交易日历取上一交易日；只比对自然日 `today` 在非交易日窗口必然塌缩。

定级 P1：用户可见的口径错误、周末+节假日必现、破坏「昨日对比」功能；不动存储、不损数据，故不到 P0。
