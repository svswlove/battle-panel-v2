## 二、F10 持久缓存（主人选型「方案二」）

### 先否掉一个方向

主人原提议「切前台时重建一次 eltdx 连接」。实测否掉：

- `F10Client` 每次调用都 `urlopen` 新建 TCP，**没有连接池**，没有「重建一次就能复用」的连接；
- 慢发生在**服务端链路**：同一进程第一次查任何代码 5.7–10s，第二次 172–297ms；
- 最慢的一步 `sector` 曾 **10062ms 直接超时**；
- 与本地连接建立无关，重建连接只是把「一次慢」变成「两次慢」。

### 真正的问题：缓存活得太短

`F10_TTL = 60.0`。面板常驻后台，1 分钟就过期，用户切回来看一眼又是冷查。

但**不能一刀切拉长**——F10 内部各字段变化频率差很远：

| 段 | 内容 | 变化频率 |
|---|---|---|
| B2 | 估值/市值/北向/盈利预测/增减持/融资融券/季度业绩/股东户数序列/行业 | 日级～季级 |
| B1-资金流 | `main_net_today` / `main_ratio_today` / `main_net_5d` | **盘中在变** |
| B1-静态 | 股东户数 / 上市日 | 季级 |

### 改法（分层）

| 对象 | 缓存 | 失效 |
|---|---|---|
| B2 整段 | **落盘** `data/cache/f10_b2/{code}.json`（原子写） | 跨交易日自动失效；删目录=强制全量刷新 |
| B1 资金流 | 内存 `_Cache` | 300 秒 |
| B1 股东户数/上市日 | 内存 `_Cache` | 交易日 |

`F10_TTL`（内存二次挡板）86400s，不再承担跨天判断。

**缓存放 core 不放插件**：插件不得持有行情缓存（CONTRACT §4.1），B1 的两个读取入口做成
门面函数 `q.f10_b1_flow()` / `q.f10_b1_finance()`，插件 `_f10_b1()` 改为调门面。

### 踩到并修掉的边界：跨零点

第一版用 `now().strftime('%Y%m%d')` 判交易日。实测：23:57 写的缓存，00:02 被判过期
→ **每天 0 点整所有 F10 一起失效重拉**，而面板凌晨也常开着。
改为「**凌晨 8 点前算前一天**」（F10 是日级数据，08:00 前不存在「今天已更新」；开盘 09:30 前留 1.5h 余量）。

### 验收（实测）

| 场景 | 改前 | 改后 |
|---|---|---|
| 首次查某代码（无缓存） | 6954–7421ms | 同（首次无法避免） |
| 同进程第二次 | 58–105ms | 0–5ms |
| **进程重启后首次** | 7000ms+（内存全清） | **94ms**（读盘） |
| B2 读盘单项 | — | **1ms** |
| B1 资金流（首次/缓存内） | 每次必走 socket | 385ms / 命中即 0 |
| 单测 | — | `test_quotes_f10.py` 11 passed（新增 2 条：跨重启仍热、跨交易日必重拉） |

### 排障入口

- 强制刷新某只：删 `data/cache/f10_b2/{glb}.json`
- 强制全量：删 `data/cache/f10_b2/` 整个目录
- 判断是否命中：看耗时（≈1–100ms=命中；7s+=冷查）
